# REE Tracker — Feature Register

Single source of truth for what the app can actually do today. Generated from a direct scan of
`ree-tracker/src/{features,pages}`, `ree-tracker-backend/src/{routes,engine,services}`, and
`ree-tracker-backend/src/sockets`. Maintained per the rule in [CLAUDE.md](CLAUDE.md) — updated on
every feature add, change, or removal, not on a schedule.

---

## App structure (2026-10 reorganization)

- [x] **Five destinations, phone-first** — **Today · Practice · Exams · Progress · Library**, one model (`layouts/navModel.js`) behind a phone bottom bar (`layouts/BottomBar.jsx`) and a desktop sidebar (`layouts/Sidebar.jsx`).
  - The active item is matched by whole first path segment, so the exam runners (`/simulator`, `/gauntlet/:n`, `/battle/:id`) light Exams; the old shell never highlighted the simulator.
  - The phone's hamburger drawer is gone. Its top bar (`layouts/PhoneHeader.jsx`) holds the focus timer's launcher (to the full-screen timer, `/focus`), connection status (to `/account#offline`) and an **account menu** (`layouts/AccountMenu.jsx`: Account · Admin for admins · Log out, which says how many unsynced answers a logout would discard).
  - The shell is an `AppShell` layout route, so navigation stays on screen while a page chunk loads. A new page opens at its top, or at the linked section.
  - The "Enter the Board Simulator?" confirm modal is gone; the same warning is a line above Start on the setup screen.
  - **Desktop Log out:** the sidebar has a Log out button beside the Account card (with the same unsynced-answers warning); it was only in the phone menu.
  - **One avatar** (`components/Avatar.jsx`) for the sidebar and the phone menu, falling back to the email's initial in both. **A rename shows at once:** Firebase updates the user in place, so the sidebar and menu kept the old name until a reload; `updateDisplayName` in AuthContext re-renders them.
  - **Connection badge:** in the collapsed sidebar the state was only a hover title; a screen reader now hears "Online"/"Offline" as it changes and can read the counts. The badge text is at least 12 px (it was 9–10 px) and plain: "3 waiting to sync", "300 saved for offline".
  - **Focus timer, full screen** (`/focus`: `pages/Focus.jsx`, `features/focus/`, `utils/pomodoroLogic.js`). The timer used to be a card crammed into the sidebar, and a dialog on phones. It is now its own distraction-free screen, outside the app's navigation.
    - **Screen:**
      - The theme's own glow and texture are the background.
      - A large SVG progress ring (`ProgressRing.jsx`, still under reduced motion) holds the time in big monospaced tabular digits (`role="timer"`; h:mm:ss for long blocks) and a line such as "Block 2 of 4 · General" or "EE section · ends 3:42 PM".
      - Controls: Reset, a large Start / Pause / Resume, and Skip.
      - Close, Full screen (where the browser supports it) and Settings.
      - Shortcuts: Space start or pause, R reset, S skip, F full screen, Esc close. They're ignored while typing or in a dialog, and Space on a focused button presses that button.
      - A screen reader hears the mode only when it changes.
    - **Modes** (Timer mode): Focus, Short break, Long break and **Paper exam**.
      - **Paper exam** is a physical mock board answered on paper, timed to the PRC section: Mathematics 5 h, ESAS 4 h, EE 6 h. "Full board in order" moves on to the next section when one ends.
    - **Shading reminder** (CELE round, 2026-10; the CELE tips: keep at least 30 minutes for shading): in a paper exam, N minutes before a section ends (Timer settings › **Shading reminder**: Off, 15, 30 by default, or 45) the timer says "30 minutes left in EE. Transfer your answers to the sheet now." with a toast, the notification and a two-note chime of its own, and the timer shows **Shading time: transfer your answers** until the section ends. It fires once per section: the mark (`shadeAlertedFor`, the section's start) is on the persisted timer, since the owner clock moves between the floating pill, the shell and `/focus`, so a reload or a second owner can't say it twice. A section shorter than the reminder never gets one (`shadeDue`, `inShadingTime`, `markShadeAlerted` in `utils/pomodoroLogic.js`; the owner effect in `hooks/usePomodoroClock.js`).
      - Its time counts as focus time for that subject, so the focus-block limit is now the longest PRC section, 6 h. It is `FOCUS_MAX_MINUTES` in `@ree/shared`, read by the API and the Recent blocks editor; it was 3 h, and a timed EE paper would have been rejected and dropped.
      - Reset, Skip (End section), and changing mode ask first during a paper exam, and it never starts by itself.
      - The screen stays on while it runs (Wake Lock).
      - The exam export's "Time this paper" opens `/focus?mode=exam&section=EE`; the link is honoured only when no block is in progress.
    - **The cycle:**
      - A long break comes after every N focus blocks (4 by default).
      - Breaks can start by themselves when a block ends, and so can the next block.
      - Skip logs a focus block's partial time if it ran at least five minutes.
      - A block that ran out while the app was closed is logged once and moves on to the next mode, paused.
    - **Sound:** a short chime when a block ends, made with Web Audio (no sound files) and on by default, with "Play test sound". The notification when a block ends opens the timer.
    - **Settings** (Timer settings): the focus, short and long break lengths (1–120 min); a long break every 2–8 blocks; auto-start breaks; auto-start focus; sound; and what the time counts toward. They edit a draft, and Save restarts the timer only if the current block's length changed.
    - **Getting there:**
      - The expanded sidebar has a slim "Focus timer" row that shows the mode and time left while a block runs; it ticks on its own, so the sidebar doesn't re-render every second.
      - The collapsed sidebar and the phone header show the timer icon, with a dot while running.
      - The floating pill's mode and time open `/focus`. A drag of 6 px or more moves it instead, and it is wide enough for 5:59:59.
      - `components/Pomodoro.jsx` is gone.
    - **One clock:** `/focus` mounts the only owner clock while it's open.
    - **Sign-out fix:** logging out cleared the session but not the timer, so the next account in the same browser inherited the running block and sent the previous account's waiting focus blocks under its own token. Now:
      - sign-out clears the block and its waiting logs, and keeps the device's lengths and toggles;
      - each logged block is stamped with the account that ran it, and only that account's blocks are sent.
    - **Saved timers carry over:** timers saved by the old version (the `isWork` shape, and the older `timeLeft` counter) load into the new mode-based shape.
    - **A block the server refuses goes to Sync issues.** A server still on the old 3 h limit refuses a 4–6 h block. It used to be dropped without a trace; now it waits in Account › Sync issues, where it can be retried once the server catches up.
    - **Old saved timers load correctly:**
      - The old version's clean-up left a block that ran out while closed stopped at 0:00. It now counts as done and moves on to the next mode. It used to load as 00:00 "in progress", so the exam link was refused and the long break never came.
      - The restored timer now reaches the screen at once. It was assigned onto the restored state, which nothing on screen heard, so after an upgrade the old saved shape showed until the next change.
    - **The sidebar row is named by what it shows** ("Focus timer, Short break 04:59"), so a voice-control user can say what they see (WCAG 2.5.3).
    - **Deploy note:** the API's new 6 h limit must ship with or before this. An old server answers a 4–6 h block with a 400, which the offline queue treats as permanent.
  - **Focus time:** pick what a focus block is for on the timer (General, Math, ESAS or EE). A finished focus block, or a paper-exam section, is logged in full; one reset, switched to a break, or cut by a new length is logged for what ran if that was at least five minutes; a break never; and one that ran out while the app was closed is still counted, dated when it ended. Pauses don't restart a block. Blocks wait with the timer (persisted) until the owning clock sends them (`POST /api/user/focus-blocks`, queued offline; the device's id for the block makes a replay land once) (`utils/pomodoroLogic.js` `focusBlockFor`, `hooks/usePomodoroClock.js`, `routes/focusRoutes.js`). **Progress › Habits › Focus time** shows minutes per day for two weeks and how the last 30 days split across the board's subjects beside the PRC weights, naming the one furthest behind ("ESAS is 30% of the board but 8% of your focus time") (`GET /api/analytics/deep/focus-time`, `services/focusTime.js`, `features/analytics/sections/FocusTime.jsx`). Under it, **Recent blocks** lists the newest ten, each with **Edit** (what it was for, and its minutes, up to the time the block spanned) and **Delete**, so a wrong subject or a timer left running doesn't skew the split (`PATCH`/`DELETE /api/user/focus-blocks/:id`, owner-scoped; `features/analytics/sections/RecentFocusBlocks.jsx`). `FocusBlock` (additive migration `20261014000000_focus_blocks`) is self-reported and display only.
  - **Weekly focus goal** (Progress › Habits › Focus time › This week; `features/analytics/sections/{FocusGoal.jsx,weeklyGoal.js}`): focus minutes since Monday (Manila) against a goal the learner sets in hours a week (presets 5, 10 and 15 h, or any amount from half an hour to 50 h), with each board subject's part of it by its weight on the board ("EE 1h 30m of 4h 30m") and the time left. Minutes marked General count toward the goal, not toward a subject. Saved with `PUT /api/user/focus-goal` (`User.weeklyFocusMinutes`, additive migration `20261018000000_weekly_focus_goal`), queued on the device offline and shown at once. It has its own route because a queued `PUT /api/user/settings` replaces an older queued one, so a goal queued offline would have dropped a queued exam plan. The focus summary carries `week { startsOn, minutes, bySubject }` and `goal { weeklyMinutes }`. Display only, like the blocks: it never feeds θ, readiness or the forecast.

- [x] **Shuffled answer choices** (`@ree/shared` `optionOrder`, `features/quiz/presentOptions.js`) — every screen a learner answers on shows a question's choices in an order drawn for that sitting, so the key's position, spatial memory and elimination by routine stop paying. Shown in their stored order, the key sat at A so often that pressing A every time scored close to half a session.
  - **Random per sitting and per question, stable within the sitting.** The order is a seeded, unbiased (Fisher–Yates) shuffle keyed on the sitting and the question, not `Math.random` on each render: re-renders, Next and Back, the answer sheet, a resume after a reload and a battle rejoin keep the order, and a new sitting brings a new one.

- [x] **Answer-sheet scanner engine (OMR)** (`features/omr/`). It reads a photo of a printed answer sheet and returns the taker's answers. It runs entirely on the device, in pure JavaScript with no libraries, so **photos never leave the phone**. It runs in a module Web Worker (`omr.worker.js`) and falls back to the main thread if a worker can't start (`createOmrClient`).
  - **Finding the sheet:**
    - an adaptive threshold copes with uneven light;
    - connected components find the four 7 mm corner squares, rejecting filled bubbles, the QR code's finder rings and text by size, solidity and square-not-disc shape;
    - the best convex quadrilateral is chosen by matching sizes, a skew limit and a paper's proportions.
  - **Straightening:** a 4-point homography maps the photo onto the sheet's own geometry (`answerSheetGeometry`, the same one the printed HTML and LaTeX sheets are drawn from).
  - **Which page and which way up:** the ID strip along the bottom edge is decoded in each orientation (0°, 90°, 180°, 270°) until its guard and parity bits check. It gives the paper size, the page number and a layout hash, so a sheet from another set, or one printed before the options changed, is refused.
  - **Paper curl:** each group of rows is re-centred on its printed bubble rings, within ±1.2 mm.
  - **Reading the bubbles:**
    - each bubble's fill is its inner disc against the white around it;
    - fills are normalised per page against the empty and the marked bubbles, so pencil, pen and dim light all read;
    - each row is a **single** mark (with a confidence), **blank**, **two marks** (invalid and scored wrong, as on the PRC sheet), or **unsure** (faint, or a possible erasure), which is flagged for a person to check.
  - **When it can't read, it says why**, with a hint for the person holding the phone:
    - no sheet ("Fit all four black squares inside the frame");
    - too small, too skewed, blurry;
    - unreadable ID strip;
    - wrong set, layout changed, wrong page, page already read.
  - **Live use:** a fast corner check on a 640 px frame (about 10 ms) drives the viewfinder. The full read at up to 2,400 px takes about 0.1 s.
  - **Tests (87):** a pure-JS synthetic sheet renderer "photographs" real sheet layouts with perspective, blur, noise, a lighting gradient, a hard shadow, vignette, paper curl and rotation.
    - On 40 seeded sheets (4, 5 and 6 options; one and two pages; A4, Letter and long bond), the test requires 99.5% of rows read exactly; the current run reads all 3,880. Every double mark must be caught, and no blank may be read as a mark.
    - A faint mark reads as unsure or blank, never as a confident wrong answer. A hard shadow edge flags the rows it crosses instead of misreading them.
    - With 2 or 3 mm of curl, 99% of rows or more still read exactly with refinement on. Without it, 3 mm of curl drops the read below 90%.
    - Every refusal reason is covered, as are the homography maths and the ID strip round trip.

## Adaptive Engine (backend, `ree-tracker-backend/src/engine/`)

- [x] **Item Response Theory (3PL)** — stateless per-item ability estimator, single unified θ + standard error per user, θ clamped to ±4 with an SE floor of 0.35 (`engine/irt.js`). **One item-parameter rule** (`itemParams`) serves the estimator, the CAT picker, calibration seeds and the θ backfill: an uncalibrated item is placed by its author rating mapped onto the θ scale (`authorB`: 1/2/3 → b −1/0/+1). Every consumer used to restate its own fallback and read `difficulty` raw as b — but authors and the AI write it on a 1/2/3 ordinal, so the typical "Core" item sat at b = 2 and θ drifted upward for everyone until calibration caught up. Missing-SE fallbacks are one `PRIOR_SE` = 1 (the population prior; four sites disagreed at 0.5/1/1/1.0), new users start there (`User.standardError` default 1.0, migration `20261002000000_user_prior_se_default`), and a purge resets SE too. `npm run audit:difficulty` reports the bank's actual difficulty distribution read-only before rollout (`engine/irt.js`, `scripts/auditDifficulty.js`, `tests/itemParams.test.js`)
- [x] **Bayesian Knowledge Tracing (BKT)** — per-topic P(mastery) driving the topic mastery heatmap, complementary to θ (`engine/bkt.js`). **Mastery decay**: BKT has no forgetting term, so a topic mastered early stayed "Mastered" however long it went untouched. `decayedMastery` decays the stored estimate toward pInit with time constant 21 d · (1 + ln(1 + n)) — ~3 weeks for a topic seen once, ~10 weeks behind fifty observations — from `UserTopicPerformance.lastPracticedAt` (new nullable column, forward-only, set by the rollup upsert and backfilled by `backfill:mastery`; migration `20261002010000_topic_last_practiced`). Display/priority only — the stored pMastery stays the pure evidence fold. The dashboard serves `masteryEffective` + `daysSincePractice`; the heatmap bands on the effective value and marks a topic "fading (Nd)" when time away has dropped it a band. Mastery bands (85/65/45) live once in `@ree/shared` (`MASTERY_BANDS`, `masteryBand`) instead of in the heatmap and the backfill separately (`services/masteryView.js`, `components/HeatmapChart.jsx`). `npm run backfill:mastery` rebuilds each learner's topic rows from their attempt history. Mastery is replayed through BKT; attempts, correct and time are counted by the live telemetry rule, so a correctly kept row is unchanged and a drifted one is corrected and reported. A missing topic key is created with its real counts. A row whose label no longer has attempts (relabelled away) is removed **only when history proves where its tally went**: answers were recorded under that label, they now count under another row, and together they cover the row's whole tally. Any other such row is left as is and reported with the reason: nothing was recorded under it (e.g. its questions were deleted), or it counts more than history holds. Each learner is rebuilt in one transaction under the same user lock telemetry takes. It used to create new keys with `correct: 0` and leave the old label's row behind (`scripts/backfillMastery.js`)
- [x] **Elo rating** — multi-player adapted rating for Arena leaderboards and Battle outcomes (`engine/elo.js`)
- [x] **Readiness score** — composite of topic coverage, accuracy, θ, consistency and blind spots, with the scoring rule extracted into a pure, unit-tested service (weights, θ normalisation derived from the estimator's own bounds, blind-spot definition and clamps) rather than inline in a route handler (`services/readinessService.js`, `readinessRoutes.js`)
- [x] **Forecasting model (v2-prc)** — the pass probability models the **PRC rule itself**: each subject's ability (per-subject `UserAbility`, or the global θ with the full prior uncertainty when a subject has no evidence) maps to an expected board score through the **test characteristic curve** of a 1,500-item random sample of the live bank (10-minute cached, tabulated on a θ grid), and 2,000 seeded Monte Carlo sittings — ability uncertainty plus 100-item sampling noise — are graded by the shared PRC rule (weighted 70% average AND no subject under 50%). Reports the strict pass probability, the **conditional** probability (average met, a subject under the floor — the most common way a strong reviewer fails, which v1's single P(θ > 0) could not see), the projected GWA with an 80% interval, each subject's projected rating, and the subject where half an SD of improvement moves the pass probability most. Weak topics rank by **decayed BKT mastery × syllabus weight** over every topic with history (v1 read only the 20 most recently touched, by log-odds of hit rate), lifted for topics answered confidently wrong and flagged when the median answer exceeds 3 minutes. ~20ms per compute behind the 60s cache, using a precompiled grader held to identical output by a 5,000-case contract test. Older-model snapshots are recomputed. Topnotcher stays a labelled θ-cutoff estimate (it is a cohort rank) (`engine/forecast.js`, `services/referenceFormCache.js`, `forecastRoutes.js`, `ForecastSnapshot.subjectForecasts` — migration `20261002020000_forecast_subject_projection`)
- [x] **Shared numerics** — dependency-free math helpers backing the above (`engine/math.js`)
- [x] **Nightly/on-demand calibration** — recalibrates item difficulty parameters from live attempt data. Reads the response matrix by keyset pagination rather than loading every attempt into memory, and writes item parameters and abilities in transactional chunks so a crash cannot leave half the bank calibrated (`services/calibrationService.js`, `npm run calibrate`)
- [x] **Targeted drill (Smart Drill v2)** — a short adaptive drill on a weak topic. With no target it drills the weakest topics by **decayed BKT mastery × syllabus weight** (the forecast's ranking), split 50/30/20 across the top three; a named topic (`topicId`, or a legacy label) drills just that. ## Platform & Offline

- [x] **Back online without a reload** (2026-10-31, `services/connection.js`, `hooks/useConnection.js`). After a network blip or a sleeping server the app used to stay broken until reloaded, even on a strong connection. Two causes:
  - **The circuit breaker:** one network failure (including the 12 s timeout) blocked every API request for 30 s with an instant `[OFFLINE]`. Only a successful response cleared it, never the browser's `online` event, and many outages (a sleeping Render server, a Wi-Fi handover) never fire that event anyway.
  - **Screens that fetch once:** a fetch that landed in that window failed, and nothing asked again.

  Now:
  - **The breaker is half-open:** after a failure, requests fail fast, but one real request goes through every 5 s. While the server is down, a light `/health` check runs by itself while the app is in view (5 s, 15 s, 30 s, then every 60 s).
  - **The first answer brings everything back.** A reconnect key goes up, and screens fetch again by themselves:
    - Today: forecast, readiness and its trend, reviews due, the loop and the plan;
    - the dashboard numbers;
    - every synced list (`useSyncedUserData`) that couldn't load.
    The answer and change queues also flush.
  - **Coming back online**, or returning to the app after 10 minutes away, wakes the server and does the same.
  - **`useNetworkStatus` means "the server is answering"** (the browser is online and the backend up). So screens that wait for a connection load as soon as the server is back, not only on the browser's `online` event.
  - **Status pill:** shows **Reconnecting…** while the device is online but the server isn't answering, and clears by itself.
  - **Boot:** the TOS and feature-flag requests wait out a cold start like the profile does (30 s). At the 12 s default they aborted first and tripped the breaker for the whole first screen.
  - **Expired sign-in token:** a 401 gets one retry with a freshly fetched token.
  - **Battles:**
    - The socket sends a current token on every reconnect. One fixed at the first connect expired after an hour, and the server refused to let it back in.
    - A refused reconnect is tried again.
    - A later drop shows the can't-connect screen after 10 s instead of spinning.
    - That screen's **Reconnect** opens a new connection instead of reloading the page.
  - **Screens whose code fails to load** (`utils/lazyWithRetry.js`): every lazy screen retries its import twice. A chunk that's really gone after a deploy reloads the page once (`vite:preloadError`, guarded to once a minute). Before, React kept the failed import and "Try again" failed the same way.
