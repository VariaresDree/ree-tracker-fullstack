# REE Tracker — Feature Register

Single source of truth for what the app can actually do today. Generated from a direct scan of
`ree-tracker/src/{features,pages}`, `ree-tracker-backend/src/{routes,engine,services}`, and
`ree-tracker-backend/src/sockets`. Maintained per the rule in [CLAUDE.md](CLAUDE.md) — updated on
every feature add, change, or removal, not on a schedule.

---

## Exam & Practice Modes

- [x] **Active Review** — per-question reveal MCQ practice with interleaving (`pages/ActiveReview.jsx`, `features/active-recall/{FlashcardMode,MCQMode,ReviewSetup,useReviewSession}.jsx`). One keypress records one answer: the option (1-4/A-D) and confidence (Q/W/E) hotkeys are owned by `QuestionCard` alone — the page used to bind them too, so both listeners fired and every keyboard answer was staged twice under two uuids the server could not dedupe (`pages/ActiveReview.hotkeys.test.jsx`)
- [x] **PRC board verdict** — one definition of pass/fail, shared by the results screen, exam history and the pass-rate KPI: a 70% general **weighted** average (Math 25 / ESAS 30 / EE 45) AND no rated subject below 50%, via `gradeBoardExam`. Subjects an exam never asked about stay unrated rather than counting as zero, and the remaining weights renormalise. Every caller used to judge the **raw** share correct as if it were the weighted average — they agree only when item counts sit in exact syllabus proportion, so a 90/60/64 sitting (71.3% raw, 69.3% weighted) passed. The results hero is now coloured by the verdict (it banded on old 70/60 score cut-offs) and shows the GWA it was judged on; Score History re-derives never-finalised sessions from their own attempts' per-subject split, so the subject floor applies there too. Previously five copies with two different thresholds, so a 55% mock showed FAILED on screen and CONDITIONAL PASS in history (`@ree/shared` `verdict`/`exam`, `services/examService.js`, `services/deepAnalyticsHelpers.js`, `features/board-simulator/{useSimulatorEngine,battleGrades,SimulatorDiagnostics}`)
- [x] **PRC exam format** — one constant for the board schedule, `PRC_EXAM_FORMAT` in `@ree/shared`: **Mathematics 100 items / 5h, ESAS 100 / 4h, EE 100 / 6h** (PRC's current schedule; Math was still 4h). The Simulator's PRC Standard sitting, its time display, the Gauntlet subject boards, battle hosting and every copy string derive from it (`PRC_TIMES`/`PRC_FORMAT_SUMMARY` in `config/examStandards.js`). Blended pools split items with one shared largest-remainder rule (`apportionItems`), so counts always sum to the total — the client turned a 10-item blend into 11. Unanswered items are recorded as LOW confidence and are never blind spots (they defaulted to HIGH, making every blank "confidently wrong"); answered-without-confidence is MED
- [x] **Server-side mock history** — every Board Simulator and battle sitting is **finalised on the server**: `POST /api/exams/sessions/:id/finalize` grades the session from its OWN recorded attempts (per-subject scores, the PRC weighted average, the verdict) and stores them — the client only describes the sitting. Sessions used to stay `IN_PROGRESS` forever, and the only per-subject record of a sitting was a device-local IndexedDB ledger, lost with a cleared browser and invisible on another device. The simulator finalises right after its telemetry lands, or queues the finalise behind the telemetry in the outbox (409 until the attempts arrive, then it runs); battles now record one session per player and finalise it server-side (they used to write session-less attempts). The dashboard's mock history reads `GET /api/analytics/deep/mock-history` (cached by the service worker for cold starts, ownership-guarded), headlines the weighted average, and derives the numbers for sittings recorded before finalisation existed. "Remove" **hides** a sitting from history rather than deleting it — a delete cascades to the attempts and would rewrite every tally and mastery estimate the sitting fed. The old local ledger is emptied once the server copy loads, on sign-out and on account deletion (`services/examHistory.js`, `components/MockBoardAnalytics.jsx`, `services/simulationLedger.js`)
- [x] **Full PRC board** — a fourth Board Simulator profile that sits the board the way PRC does: **Mathematics, then ESAS, then EE**, each a 100-item sitting on its own PRC clock (5h / 4h / 6h, from `PRC_EXAM_FORMAT`), with a break between sections for as long as the learner likes. Results are **withheld until the last section** — between sections only progress is shown, never scores or the answer review — then the board result: the PRC weighted average, the verdict, each subject against the 50% floor and the total time. All three sections report under ONE server session, so the server finalises the board from all 300 attempts at once; the earlier sections leave it open. Progress between sections is kept for 7 days (and within a section by the simulator's crash-safe draft, resumable from the break screen); a re-submitted section can never skip one. Abandoning keeps the finished sections in analytics but keeps the half-board out of mock history. Previously the simulator offered single-subject sittings or one 100-item blend in 5 hours (`features/board-simulator/{fullBoard,FullBoardScreens}`, `pages/BoardSimulator.jsx`)
- [x] **Board Simulator** — full timed mock exam: config → live run → post-exam diagnostics, exportable exam paper PDF. Crash-safe: the resumable draft carries answers, confidences, bookmarks, current item **and per-question timing**, is retained through resume, and is cleared only once the attempts are durably synced or queued — a failed submit of any kind (5xx, auth, parse error) defers the batch to the offline outbox instead of discarding it (`pages/BoardSimulator.jsx`, `features/board-simulator/{SimulatorConfig,SimulatorActive,SimulatorDiagnostics,useSimulatorEngine,examPaper,battleGrades}.jsx`)
- [x] **Placement test (diagnostic CAT)** — a ~20-minute adaptive sitting: Mathematics 5 / ESAS 6 / EE 8 items at most (15–19 in all, roughly 25/30/45), each subject stopping early once its estimate reaches SE ≤ 0.45 after three items. The server picks every item at the learner's current per-subject estimate — Fisher information, discounted for topics already covered, then a random pick among the best three — grades it, and reveals nothing until the end, so the endpoint cannot be used to fish for an answer key and only the item currently being asked can be answered. The result projects each subject through the bank's characteristic curve (Board-ready ≥70 / Developing ≥50 / Foundation) and the weighted average against the PRC marks; for an account with fewer than 30 prior answers it **seeds** per-subject abilities and θ, so practice, drills and the forecast start calibrated instead of from the θ = 0 every new account shared — an established account's placement is reported, not imposed. Resumable for 7 days (state lives in `ExamSession.config`, mode `DIAGNOSTIC`, no schema change); attempts are recorded once at the end with deterministic ids, and finishing is idempotent. Prompted on the dashboard while an account is new or a sitting is unfinished — skippable, "Not now" remembered per account — and retakeable from Profile → Settings (`pages/Diagnostic.jsx`, `features/diagnostic/PlacementPrompt.jsx`, `routes/diagnosticRoutes.js`, `services/diagnosticService.js`, `engine/cat.js`)
- [x] **CAT item selection** — `POST /api/exams/next-item` and the placement test draw from one candidate query (`services/catCandidates.js`): a random sample windowed around θ (calibrated items within ±1.5; uncalibrated items placed by author rating), with recently seen and in-session items excluded in SQL and subjects matched by every stored spelling. It used to read `take: 80` unordered rows — the same rows every call — match the subject by raw equality, and always serve the single most informative item, so every learner at a given θ got the identical first question
- [x] **Gauntlet** — distraction-free timed drill with resume-from-cache and its own diagnostics. A run is never lost at submit: offline, a dropped connection **and a 5xx** all defer it to the durable outbox; only a permanent 4xx ends on the error screen. `POST /api/exams/grade` answers **503** when it graded the run but could not save it — it used to log the failure and answer 200, which the outbox read as delivered and the idempotency layer replayed for 24h, so one transient DB error silently discarded the whole run (`pages/Gauntlet.jsx`, `features/gauntlet/{useGauntletEngine,GauntletDiagnostics}.jsx`, `routes/examRoutes.js`, `tests/examGradeRoute.test.js`)
- [x] **Shared answer surface** — one `QuestionCard` component (prompt, confidence selector, choice grid, hotkeys, reveal animation) reused identically across Active Review, Board Simulator, Gauntlet, Combat, and the offline Quiz Launcher (`features/quiz/QuestionCard.jsx`)
- [x] **Exam-focus layout** — collapsible high-alert header, distraction-free chrome for any active exam surface (`layouts/ExamLayout.jsx`)
- [x] **Isolated exam clock** — one countdown component shared by Board Simulator and Gauntlet, driven by an absolute deadline so it cannot drift and self-corrects after a throttled background tab. It owns its own interval and re-renders only itself, so a tick no longer reconciles the question, its LaTeX subtree, or the per-question navigator (`components/exam/ExamClock.jsx`)
- [x] **Offline CAQ Quiz Launcher** — import a third-party `.quiz`/`.caq` archive (ZIP) from the user's device and run it as an untimed practice exam entirely client-side: zero server contact, zero telemetry, zero effect on θ/streak/analytics. Parses to a normalized shape, skip-and-counts malformed records rather than failing the file, and collapses byte-identical duplicate answer choices (a real defect observed in third-party files) so the question stays answerable. Statically verified to never import the telemetry/store/scoring modules (`features/quiz-launcher/{caqParser,useCaqSession,QuizFilePicker,QuizLauncherTab,CaqRunner,CaqResults}.js(x)`, entry point: Materials Hub → Quiz Launcher tab, lazy-loaded)

## Analytics & Forecasting

- [x] **Dashboard** — ordered by the questions a reviewer asks (`pages/Dashboard.jsx`). **Today panel** first: the **Board Readiness Index** with its breakdown (coverage, accuracy, ability, consistency — the API always returned it and nothing rendered it), the **PRC-rule pass probability** with projected average and floor risk, **today's target** progress, and an ordered **Next best actions** list — due spaced reviews, the forecast's top fix (blind spot or targeted drill), what's left of today's target, a timed mock — each launching the right session; plus the placement-test invite for new accounts (`features/today/{TodayPanel,todayActions}`). Then a 4-tile KPI strip (accuracy, answered, time per question, streak), ability trajectory beside the board forecast, mastery heatmap (tiles start drills) beside the confidence matrix, prescription beside daily targets, and the mock ledger. Every row ends in an action — "Fix this" starts a blind-spot drill on the topic; a time sink opens its formula cards or a drill. Per-exam blind spots and slow items existed on the results screen; nothing tracked them across sessions. The per-topic signal query is shared with the forecast's weak-topic ranking (`features/analytics/WeakSignalsPanel.jsx`, `services/topicSignals.js`, `GET /api/analytics/deep/weak-signals`)
- [x] **Calibration curve** — confidence-vs-actual-accuracy visualization (`features/analytics/CalibrationCurve.jsx`, `calibration.js`)
- [x] **Exam performance card** + **prescription panel** — post-exam summary and "3 actions to close your widest gaps" recommender (`features/analytics/{ExamPerformanceCard,PrescriptionPanel}.jsx`). Actions in order of leverage: **Blind spot** (a topic answered confidently wrong), **Targeted drill** (the costliest gap), **Spaced review** (the due queue), **Formula cards** (deep-links to that topic's formula cards in the reference vault), **Read source** (a topic barely started)
- [x] **Ability trajectory (θ) chart** + **board forecast card** — readiness velocity over day/week/month, beside the PRC-rule forecast: strict pass probability, projected weighted average with its likely range, a conditional-result warning, and each subject's projected rating against the 50% floor and 70% line with the most-leverage subject marked. The chart tooltip shows θ only — it used to label a linear (θ+4)/8 "Pass Probability", a third θ→% mapping on the same page that disagreed with the forecast (`features/analytics/TrajectoryCard.jsx`, `components/ThetaVelocityChart.jsx`)
- [x] **Explanation review** — AI-explanation audit queue for flagged/pending items (`features/analytics/ExplanationReview.jsx`)
- [x] **Consistency matrix / activity calendar** — Manila-day heatmap of questions answered (`features/profile/ActivityCalendar.jsx`, backend `analyticsRoutes.js`)

## Adaptive Engine (backend, `ree-tracker-backend/src/engine/`)

- [x] **Item Response Theory (3PL)** — stateless per-item ability estimator, single unified θ + standard error per user, θ clamped to ±4 with an SE floor of 0.35 (`engine/irt.js`). **One item-parameter rule** (`itemParams`) serves the estimator, the CAT picker, calibration seeds and the θ backfill: an uncalibrated item is placed by its author rating mapped onto the θ scale (`authorB`: 1/2/3 → b −1/0/+1). Every consumer used to restate its own fallback and read `difficulty` raw as b — but authors and the AI write it on a 1/2/3 ordinal, so the typical "Core" item sat at b = 2 and θ drifted upward for everyone until calibration caught up. Missing-SE fallbacks are one `PRIOR_SE` = 1 (the population prior; four sites disagreed at 0.5/1/1/1.0), new users start there (`User.standardError` default 1.0, migration `20261002000000_user_prior_se_default`), and a purge resets SE too. `npm run audit:difficulty` reports the bank's actual difficulty distribution read-only before rollout (`engine/irt.js`, `scripts/auditDifficulty.js`, `tests/itemParams.test.js`)
- [x] **Bayesian Knowledge Tracing (BKT)** — per-topic P(mastery) driving the topic mastery heatmap, complementary to θ (`engine/bkt.js`). **Mastery decay**: BKT has no forgetting term, so a topic mastered early stayed "Mastered" however long it went untouched. `decayedMastery` decays the stored estimate toward pInit with time constant 21 d · (1 + ln(1 + n)) — ~3 weeks for a topic seen once, ~10 weeks behind fifty observations — from `UserTopicPerformance.lastPracticedAt` (new nullable column, forward-only, set by the rollup upsert and backfilled by `backfill:mastery`; migration `20261002010000_topic_last_practiced`). Display/priority only — the stored pMastery stays the pure evidence fold. The dashboard serves `masteryEffective` + `daysSincePractice`; the heatmap bands on the effective value and marks a topic "fading (Nd)" when time away has dropped it a band. Mastery bands (85/65/45) live once in `@ree/shared` (`MASTERY_BANDS`, `masteryBand`) instead of in the heatmap and the backfill separately (`services/masteryView.js`, `components/HeatmapChart.jsx`). `npm run backfill:mastery` rebuilds each learner's topic rows from their attempt history. Mastery is replayed through BKT; attempts, correct and time are counted by the live telemetry rule, so a correctly kept row is unchanged and a drifted one is corrected and reported. A missing topic key is created with its real counts. A row whose label no longer has attempts (relabelled away) is removed **only when history proves where its tally went**: answers were recorded under that label, they now count under another row, and together they cover the row's whole tally. Any other such row is left as is and reported with the reason: nothing was recorded under it (e.g. its questions were deleted), or it counts more than history holds. Each learner is rebuilt in one transaction under the same user lock telemetry takes. It used to create new keys with `correct: 0` and leave the old label's row behind (`scripts/backfillMastery.js`)
- [x] **Elo rating** — multi-player adapted rating for Arena leaderboards and Battle outcomes (`engine/elo.js`)
- [x] **Readiness score** — composite of topic coverage, accuracy, θ, consistency and blind spots, with the scoring rule extracted into a pure, unit-tested service (weights, θ normalisation derived from the estimator's own bounds, blind-spot definition and clamps) rather than inline in a route handler (`services/readinessService.js`, `readinessRoutes.js`)
- [x] **Forecasting model (v2-prc)** — the pass probability models the **PRC rule itself**: each subject's ability (per-subject `UserAbility`, or the global θ with the full prior uncertainty when a subject has no evidence) maps to an expected board score through the **test characteristic curve** of a 1,500-item random sample of the live bank (10-minute cached, tabulated on a θ grid), and 2,000 seeded Monte Carlo sittings — ability uncertainty plus 100-item sampling noise — are graded by the shared PRC rule (weighted 70% average AND no subject under 50%). Reports the strict pass probability, the **conditional** probability (average met, a subject under the floor — the most common way a strong reviewer fails, which v1's single P(θ > 0) could not see), the projected GWA with an 80% interval, each subject's projected rating, and the subject where half an SD of improvement moves the pass probability most. Weak topics rank by **decayed BKT mastery × syllabus weight** over every topic with history (v1 read only the 20 most recently touched, by log-odds of hit rate), lifted for topics answered confidently wrong and flagged when the median answer exceeds 3 minutes. ~20ms per compute behind the 60s cache, using a precompiled grader held to identical output by a 5,000-case contract test. Older-model snapshots are recomputed. Topnotcher stays a labelled θ-cutoff estimate (it is a cohort rank) (`engine/forecast.js`, `services/referenceFormCache.js`, `forecastRoutes.js`, `ForecastSnapshot.subjectForecasts` — migration `20261002020000_forecast_subject_projection`)
- [x] **Shared numerics** — dependency-free math helpers backing the above (`engine/math.js`)
- [x] **Nightly/on-demand calibration** — recalibrates item difficulty parameters from live attempt data. Reads the response matrix by keyset pagination rather than loading every attempt into memory, and writes item parameters and abilities in transactional chunks so a crash cannot leave half the bank calibrated (`services/calibrationService.js`, `npm run calibrate`)
- [x] **Targeted drill (Smart Drill v2)** — a short adaptive drill on a weak topic. With no target it drills the weakest topics by **decayed BKT mastery × syllabus weight** (the forecast's ranking), split 50/30/20 across the top three; a named topic (`topicId`, or a legacy label) drills just that. Items are chosen like a CAT: by Fisher information at the learner's ability in that subject, from a window of ±1 around θ that widens only when the topic is thin, picked randomesque among the most informative so two drills differ; uncalibrated items are placed by their author rating on the θ scale. **Blind-spot mode** leads with the questions answered confidently wrong. Never serves a flagged item or one seen in the last 24h, and returns items **with their answers** — the old route stripped `answer`, so the client marked every drill MCQ wrong and flashcards revealed a blank; it also ranked by raw accuracy on the legacy subtopic string and did not exclude flagged questions. Launched from the prescription panel (Targeted drill / Blind spot), any heatmap tile ("Drill Calculus"), the analytics deep dive (Targeted / Blind-spot drill) and Active Review's "Weak points" — whose custom scope used to fall through to a plain Mathematics library session (`engine/drill.js`, `routes/smartDrillRoutes.js`)
- [x] **Spaced repetition (SRS)** — server-authoritative SM-2, scheduled inside the telemetry write transaction from evidence every surface already records: a miss or a low-confidence answer starts a card, any later answer to that question moves it, and quality comes from correctness × confidence (a confident miss — a blind spot — scores 0 and returns soonest). Due dates fall on Manila midnights. One read + one bulk upsert per chunk, so a replayed batch never reschedules twice. Active Review shows **"N questions due for review"** (capped at 30 per session, overdue count, or when the next review falls due once the queue is clear) and runs the queue as a normal session. Previously dead end to end: the client SM-2 hook was imported nowhere, `POST /srs/review` trusted client-computed intervals and had no callers, so no card was ever written and `/due` was always empty — the hook, that route, `/stats` and its schema are deleted (`engine/srs.js`, `services/telemetryService.js`, `routes/srsRoutes.js` `GET /due` + `GET /summary`, `hooks/useSrsSummary.js`, `features/active-recall/ReviewSetup.jsx`)

## Content Pipeline

- [x] **AI question generation** — Gemini-backed generation from syllabus targets or uploaded material, with strict JSON/LaTeX rules. The model labels each question from the **live** taxonomy (`GET /api/config/tos`, re-pulled whenever the Library opens). A picked topic is applied verbatim, and an "All topics" label is snapped to the live spelling. The prompt used to read the static fallback list in `config/constants.js` — 28 EE topics the Topic table doesn't have — so AI questions went live as "Transient Response" / "AC Impedance" with no topic (`aiRoutes.js`, `services/geminiApi.js`, `services/liveTaxonomy.js`, `utils/topicLabels.js`, `features/library/{LibraryIngestion,useAIIngestion}`)
- [x] **AI reference card generation** — same pipeline for constants/formulas/concepts
- [x] **PDF/image ingestion** — OCR-adjacent text extraction feeding AI generation (`features/library/pdfWorker.js`)
- [x] **LaTeX rendering** — KaTeX via remark-math/rehype-katex, with a math-delimiter normalizer at ingestion so malformed LaTeX doesn't reach the database (`components/LatexRenderer.jsx`, `utils/mathDelimiters.js`)
- [x] **Taxonomy resolver** — shared Subject/Topic/Subtopic hierarchy backing questions, reference cards, and the heatmap (`topicResolver.js`). Every live-question write resolves its topic **within the question's own subject**: manual add, single approve, Accept All, admin edits and the legacy un-flag, through `resolveQuestionTopic` / `crossSubject: false`. When the subject has a taxonomy, a label outside it is **refused** (400, or `unknown-topic` in bulk) rather than published with `topicId` NULL, which left it invisible to topic-targeted Smart Drill and CAT. Telemetry keeps the cross-subject fallback for mislabelled attempts. `npm run link:topics` (dry run) / `link:topics:apply` links untagged questions to **existing** topics by exact name/alias within the subject. It never creates topics. Labels the stale dropdown minted get reviewed remaps to existing topics (`LABEL_REMAPS`: "Transient Response" → "Electrical Transient Analysis", "AC Impedance" → "Electric Circuits 2"). Anything still unmatched is reported. The run is followed by `backfill:mastery`. `migrate:taxonomy` refuses to seed while the Topic table holds curated topics its PRC seed doesn't define, which is the case once the TOS editor manages the taxonomy, as production does. Seeding there would create parallel topics and split analytics; `--force` overrides (`scripts/{linkQuestionTopics,migrateTaxonomy}.js`)
- [x] **Topic respelling follows through** — renaming a topic in the TOS editor to a spelling with the same key (e.g. "electric circuits 2" → "Electric Circuits 2") keeps the Topic row and now updates, in the same transaction, the labels that copy its name. Its questions' `subtopic` takes the new name. Each learner's `UserTopicPerformance` row under the old spelling is renamed in place with every field kept. If the learner already has a row under the new spelling, the two are merged from attempt history by `backfill:mastery`'s own rules: counts and mastery are rebuilt from history (never added, so nothing is counted twice), and the old row is removed only when history proves it is covered. Any other old row is kept and logged. The merge takes the same per-user lock telemetry does. Before this, telemetry kept writing the old spelling while `backfill:mastery` folded history under the new one and deleted the old row every run, so the forecast and heatmap saw one topic split in two, and question filters by the new name missed the topic's questions. Historical `QuestionAttempt.subtopic` is not rewritten. The save also clears the question-bank cache (the offline pack checksum covers `subtopic`) and the affected learners' dashboard, readiness and forecast caches. The response reports `relabeled` counts. The backfill's fold and proof moved from the script into `services/masteryRollups.js` so both paths share them (`routes/configRoutes.js`, `services/{topicRelabel,masteryRollups,topicResolver}.js`)
- [x] **PRC syllabus weighting** — dynamic Table-of-Specification weights per subject, canonically keyed and sourced from the shared package so the client's weighted rating and the server's blended sampler cannot diverge (`utils/tosWeights.js`, `SyllabusWeight` model, `@ree/shared`)
- [x] **Shared rules package (`@ree/shared`)** — npm workspace holding every business rule that must agree between client and API: the board verdict, subject naming, syllabus weights, Manila day bucketing, LaTeX/choice-prefix normalisation, and analytics thresholds. Cross-package contract tests assert the same facts from both sides, so a drift or a broken link fails CI (`packages/shared`, `src/test/sharedContract.test.js`, `tests/sharedContract.test.js`)

## Multiplayer & Social

- [x] **Arena** — global peer leaderboard, served from a periodically rebuilt snapshot. The rebuild is single-flight (concurrent stale requests share one pass instead of each launching a full table aggregate), demand-gated so an idle instance stops re-scanning, and escalates repeated failures instead of silently falling back forever (`pages/Arena.jsx`, `leaderboardRoutes.js`, `services/leaderboardService.js`)
- [x] **Battle (real-time multiplayer)** — Socket.IO-backed lobby, live opponent state, server-authoritative grading and scoring. A failed attempt write after the match is graded is retried in the background (2s/8s/30s, idempotent by the deterministic `battleId:userId:questionId` ids) instead of being logged and dropped, which left the battle out of the learner's analytics (`services/retryInBackground.js`). Every event is rate-limited per socket; `battle-submit` only ever reads an existing lobby (so a flood of forged ids cannot evict live battles) and requires the battle to be `IN_PROGRESS`; the battle start time is persisted, so a restart mid-match no longer zeroes every participant's elapsed time and randomises Elo placement (`pages/BattleLobby.jsx`, `battleRoutes.js`, `sockets/battleSocket.js`)
